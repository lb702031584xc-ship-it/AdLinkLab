# 判定口径统一（P2-2）

> 唯一口径：**`verdict = min(条款门禁, 盈利, 流量门, 初筛)`** —— 四条腿中最弱的一条决定最终判定。
> 本文件是口径的唯一书面来源；口径的唯一代码实现是
> `packages/shared/src/verdict.ts` 的 `synthesizeVerdict`（前后端共用），
> `apps/api/src/ai/blueprint.ts` §7 与工作表一票否决横幅都调它，不许各写一遍 min 逻辑。
> `apps/api/src/ai/pipeline.ts` 的 `synthesizeDecision` 是 AI 分析的评分制决策
> （DO_NOT_RUN/MANUAL_REVIEW/TEST/RUN），与本 min 口径是两套不同的判定，不要混用。

## 四条腿

| 腿 | 来源 | 通过 | 未知 | 失败 |
|---|---|---|---|---|
| 条款门禁 | Terms 解析 | 条款未禁止 / 明确允许 | 无法判定（除品牌词竞价、直接链接的“未禁止 = 通过”外） | 条款明确禁止 |
| 盈利 | 代码公式（K3）+ $8 佣金门槛 | 盈利模型通过 | 关键输入缺失，无法测算 | 测算为亏 / 佣金低于 $8（经济性 stop，非政策禁止） |
| 流量门 | P0-1 流量需求门 | 需求达标 | 无法查证 → **unknown，不判 fail** | 需求明显不足 / 自然≥1000 且付费=0（kill 档） |
| 初筛 | 工作表第 ① 步零成本杀法则 | 全部通过 | 未跑完（不拦） | 任一条命中 → kill |

## 规则

1. 任一腿失败 → 最终判定失败（STOP / 不建议投）。
2. 无失败但有谨慎 → 谨慎（CAUTION）。
3. 无失败/谨慎但有未知 → 未知（UNKNOWN），必须标注“哪条腿未知 + 补什么证据”；unknown 永不降级为失败（K4）。
4. 四条腿都通过 → 才可判定通过（GO）。
5. 盈利测算只用代码公式（K3），绝不用 LLM 文本公式；流量门 unknown 绝不改写成 fail（K4）。
6. 横幅合成（工作表判定区）按四条腿合成，与本口径一致；blueprint §7 按条款 + 盈利两条腿合成（流量门/初筛在推演流程里不跑，不传即不参与）。

## 与 P1-5 / P2-6 的关系

- P1-5 测试节奏清单、P2-6 诊断码是**执行期**的节奏/诊断，不参与事前判定口径。
- P2-9 每日预警的 P0/P1/P2 分级复用同一规则源，不另设判定口径。
